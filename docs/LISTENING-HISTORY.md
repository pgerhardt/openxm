# Local listening history

OpenXM records estimates from headset playback reports while the app is connected. This implements daily totals and a usage-session log, part of [Sony's Activity feature](https://helpguide.sony.net/mdr/hpc/v1/en/contents/TP1000524578.html). A separate, default-off song-history option saves listening content with conservative source checks. A short Spotify-to-XM3 recording test passed, with earlier intermittent metadata failures still unresolved. Activity/location context, badges and Sony-account sync remain missing.

## Recording and presentation

- Both daily recording and the separate **Also keep session times** preference default to off. Existing daily recording is preserved when upgrading; session recording is never enabled by migration or import.
- The controller samples on playback/connection changes and every 15 seconds. Only actual playback replies refresh the 90-second validity window. Battery, volume and metadata updates do not renew it. Unknown, unavailable, malformed or stale playback status stops sampling. V2 reports identifying a call are excluded; the V1 layout has no corresponding call field.
- Adjacent samples contribute only when the previous sample was playing, the device/model match and the interval is positive and no longer than 30 seconds. Pause ends a session at the observed pause time. Disconnects, device changes, app restarts, sleep gaps and lost status end continuity without backfilling unobserved time. These are estimates, not measurements of audio exposure or wearing time.
- Session IDs are random UUIDs, not device identifiers. Records contain the model, start/end instants, recorded civil date and time zone. Intervals split at local midnight, including daylight-saving boundaries. The browser shows recorded time-zone abbreviations and seconds, so short intervals and repeated hours remain distinguishable.
- Browse History has week/month/year charts, model filters, daily totals and a paged session log. Clearing session times preserves daily totals and recording preferences. Turning recording off retains saved history.
- Daily totals are kept for up to one year. Session detail is kept for up to one year or the latest 12,000 sessions, whichever limit is reached first. Discarding old session detail does not erase retained daily totals. Song names, device addresses and locations are not saved in this history.

## Storage and backup

`~/Library/Application Support/SoundConnect/listening-history.json` uses version 2, with a bounded 8 MB document. Version 1 daily-only files still load; their original daily values and recording preference are preserved. No old session times are inferred. Writes are atomic. Invalid files remain in place with recording disabled until the user explicitly resets history, which preserves the unreadable original aside.

Version 3 OpenXM app-data backups include daily totals and session detail when history is selected, and song history only through a separate export selection (off by default). No recording preferences are exported. The portable file limit is 32 MB. Version 1 and 2 backups remain readable; omitted data is not erased. Export/import UI explicitly identifies the included data.

Matching session UUIDs retain the longer snapshot only when start, model, day and time zone agree. Conflicting identities stop the restore. Distinct overlapping intervals contribute their union to daily coverage. The merged total is the larger of existing/imported daily estimates and known session coverage; opaque daily-only estimates are never added together. This is deliberately conservative when combining old daily-only history with newer sessions.

Restore review checks daily values, session records and both recording preferences again before writing. The existing app-data recovery workflow preserves exact original files and rolls back synchronous write failures before publishing restored memory. Import never enables recording or resumes an imported session.

## Metadata prerequisite — 2026-10-30

Bluetooth track text now publishes as a complete observation. V1 stages title, album and artist in query order; starting a new batch clears the previous observation. Track-change notifications, failed reads, malformed text and out-of-order replies invalidate the entire batch. Missing fields are never inherited from another track. Batches expire after 15 seconds, and published Bluetooth metadata expires after 90 seconds without a new complete observation. Playback/volume replies do not renew metadata freshness.

The pinned [V1 reference](https://github.com/mos9527/SonyHeadphonesClient/blob/68dfced0403b38114b77f2b374e606ce12a206a8/libmdr/include/mdr/ProtocolV1T1.hpp) defines separate name queries and text-free name notifications. The [V2 reference](https://github.com/mos9527/SonyHeadphonesClient/blob/68dfced0403b38114b77f2b374e606ce12a206a8/libmdr/include/mdr/ProtocolV2T1.hpp) defines four name fields in each metadata reply/notification. All four are now decoded and validated before publishing the displayed title/album/artist; the fourth is not exposed. Invalid UTF-8 is rejected, while valid composed and decomposed accents and multibyte names are preserved. A sequential V1 batch is not a protocol-provided track ID or an atomic headset snapshot: undelivered track-change notifications can still limit correlation.

Eight additional regression tests cover complete/partial batches, track changes between replies, wrong order, stale batches, missing values, UTF-8, malformed fourth fields, independent metadata expiry and avoiding an observation loop when expiry makes no change. The full fixture-enabled suite passes **250 tests in 35 suites**. The Mac media helper already replaces full snapshots, and the preceding live check verified accented text on that path. Physical Bluetooth text retrieval remains unverified because the XM3 did not return title/album/artist text in the live check.

This is a verified inactive case, not a verified playing/routing case. No audio tap, capture, output change or playback command was used.


## Song history — 2026-10-30

Song history is an independent opt-in, off by default. Enabling daily totals or session times never enables it. Its separate `listening-content.json` version 1 file stores available title/artist/album, metadata source (headphones or Mac app), app bundle ID for Mac sources, model, random record UUID, start/end instants, civil date and recorded time zone. It does not store Bluetooth addresses, process IDs, artwork, audio or locations. Records retain their Unicode bytes, including composed and decomposed accents. Optional absent fields stay absent. Text is limited to 512 UTF-8 bytes per field, app IDs to 256, storage to 16 MB, and history to one year or the newest 5,000 records. Invalid originals remain preserved, and explicit reset retains a copy.

Source policy:

- Fresh, complete headphone metadata is preferred, with a fresh music-playing status. The existing Bluetooth batch and freshness limitations still apply.
- Mac fallback requires a fresh, bounded `get --no-artwork` read from the bundled helper. Player PID, bundle ID, title/artist/album and playing state must agree with the full displayed stream snapshot both before and after the read. The query has a four-second timeout and 16 KB output limit; output is not persisted unless the record is accepted.
- Core Audio must identify that exact process and bundle, report active output IO, and report exactly one output device whose Bluetooth transport and address-based output UID match the selected headphones. Default output, names, aggregate devices, multiple outputs, missing process information and unknown routes are not sufficient. Process IDs and device addresses are used transiently, never written to song history. Apps whose media owner and audio process differ may leave gaps; the app does not guess a relationship.
- Samples normally arrive every 15 seconds. Invalid/missing metadata, uncertain source, device changes, sleep, stale playback, disconnection and gaps longer than 30 seconds end continuity. A fresh headphone pause closes an existing interval at the observed pause. If the Mac player reports paused first, its loss of playing evidence ends continuity at the last verified sample; the later headphone pause does not backfill that gap. Track changes end or split intervals; intervals split at recorded local midnight. These are estimates, not exact track lengths, plays, exposure or wearing time. A Mac track change can leave an unrecorded gap while source evidence is renewed.

The native browser supports week/month/year, model and source filters, Unicode-aware search, 60-record paging, source labels, seconds and recorded time zones. Song-only clearing leaves daily/session history and recording preferences intact. Turning recording off preserves saved songs.

Version 3 backup review includes a separate song-history selection and preview. Matching UUIDs may extend an interval only if all identity and content fields agree; conflicts stop restore. Import does not enable recording or add song intervals into daily totals. Versions 1 and 2 cannot carry song data and leave current song records intact. Restore checks the original records and recording switch again, preserves exact original bytes, and uses the existing multi-file synchronous rollback before publishing in-memory results. As before, this is not a crash-atomic transaction across files.

Ten regression tests cover default-off behavior, Unicode byte preservation and reload, omitted identifiers, track changes and missing fields, pauses, route rejection, process identity, stale/call status, discontinuities, midnight, retention/size limits, corrupt files, conflicting/extended snapshots, old backup versions, separate export/import selection, stale reviews and a failure on the third restored file. The full fixture-enabled suite passes **260 tests in 36 suites**. An isolated native preview with 70 synthetic records verified accented display and search (including composed input finding decomposed text), source/model filtering, paging beyond 60, returning to the top after filters, and song-only clearing with the opt-in preserved. No normal user history was enabled or changed by these checks.

The implementation checks above preceded the physical test below. Phone-to-headphone Bluetooth text, longer recordings, track changes during recording, and later-firmware behavior remain unverified. This implementation does not establish complete Sony Activity parity.
