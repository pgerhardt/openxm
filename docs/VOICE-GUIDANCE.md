# Voice-guidance language discovery, downloads and installation

OpenXM reads V1 voice-guidance capabilities, installed language, on/off availability, language-update status, download-service identifiers and the update method. The native Voice Language Packages sheet supports Sony discovery, original package/notice preservation, read-only preparation, and an **experimental installation/resume/verification workflow** for the international WH-1000XM3. The native coordinator and wire transactions pass scripted tests; actual XM3 service/package validation and physical language installation remain unverified. This is progress toward Sony-app parity, not completed hardware validation.

## Evidence

The WH-1000XM3 4.5.2 capture from 2026-10-29 contains this literal table-2 capability reply:

```text
41 01 01 01 0F 01 02 03 04 05 06 07 08 09 0A 0B 0D 0F 10 F0
```

It advertises on/off switching, language switching and 15 language codes. In order: English, French, German, Spanish, Italian, Portuguese, Dutch, Swedish, Finnish, Russian, Japanese, Brazilian Portuguese, Korean, Turkish and Chinese. This establishes the advertised list on that headset/firmware only; it does not establish package availability or Japan/China-model compatibility. The saved capture does not include the installed-language, service-list or update-method replies. Those queries still need a live connected-headphone result, including separate evidence on 2.0.0.

Sony's [WH-1000XM3 voice-guidance help](https://helpguide.sony.net/mdr/wh1000xm3/v1/en/contents/TP0001703077.html) documents changing voice language through its app. The protocol was independently implemented from the pinned research snapshot `egaebel/sony-headphones-hack@ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed`. No Sony reference code is bundled.

Bluetooth discovery uses only `GET` commands and performs no automatic network download. Queries are gated by the parsed capability, and replies match table, command, selector **and detail**. The on/off control additionally requires availability `ENABLE=0`; unknown availability never enables a write. Changing a supported capability clears stale language/service information, and disconnect/reset clears all of it.

The parser commits only complete values, rejects duplicate languages/service entries, truncated strings, trailing bytes and invalid boolean flags, and retains unknown language/method codes without assigning them another meaning. Download identifiers must be 1–128 ASCII letters, digits, hyphens or underscores. Other forms are unavailable until their actual semantics are investigated; they are never normalized into URLs. Unknown download methods invalidate the previous service descriptor. CSR update parameters must be exactly two bytes; other modules remain opaque diagnostic data. Required time is retained in wire units until its conversion is established, so no time estimate is shown.

## Native package downloads

Choosing Check Sony takes a new empty-state device snapshot and reads the ordinary firmware category/service in the same exclusive Bluetooth transaction. Production discovery requires V1, model `WH-1000XM3`, category `HP001`, ordinary firmware service `MDRID291600`, a firmware version and an exact advertised language/service entry. Neither a displayed language nor a model name can substitute for that mapping. Japan/China firmware services are rejected, and the ordinary firmware service cannot be reused as the language service.

The reference request builder [`automagic/l.java`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/automagic/l.java) constructs `https://info.update.sony.net/<category>/<service>/info/info.xml`. Its rule reader [`automagic/k.java`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/automagic/k.java) evaluates device model, firmware version and serial locally; these values are not sent as URL parameters. OpenXM supports the six comparison operators, numeric firmware components, string model equality and numeric serial ordering; unknown rules do not establish eligibility. Multiple eligible packages, unknown control structures, closed service status, malformed hashes/sizes and cross-service URLs are rejected.

Only envelope decoding is shared with firmware. The existing firmware XML/model/region checks remain restricted to international XM3 firmware. SHA-1 envelope consistency is not a publisher signature. Native URLSession requests and every redirect are restricted to HTTPS on the exact Sony service path; no cookies or credentials are used. Sony's HTTP distribution URLs are upgraded to HTTPS. Transfers have bounded sizes and cancellation.

Download Package verifies the complete byte count and SHA-1 before publishing an archive containing `package.bin`, the original `metadata.enc`, and `provenance.json` with source URLs, language/service, firmware at discovery, package version, size, SHA-1 and computed SHA-256. The provenance record omits the device serial and Bluetooth address. Distinct metadata/device contexts get separate folders. Existing archives are revalidated and never overwritten, even if corrupt. Partial transfers are not published. Voice packages cannot be passed to the pinned firmware installer.

Check Sony also reads preparation instructions from the eligible package's `Descriptions` and fetches its referenced `InstallType="notice"` asset, when present. Notice URLs and redirects stay within the exact Sony service; the original byte count and SHA-1 must match before parsing or display. Unknown distribution types, duplicate notices, missing default languages, duplicate localized instructions and malformed references are rejected. Instructions from an ineligible condition are never attached to a selected package.

The native sheet displays Sony's preparation text and notice as selectable plain text, with independent language/locale pickers. English/UK is preferred when provided, otherwise the declared default is used; no translation or replacement text is invented. HTML inside a text field remains literal text. Unsupported markup, document types/entities, missing default locales, duplicate locales and oversized text are rejected. The observed notice's whitespace before its XML declaration is trimmed only for parsing; original bytes remain unchanged for hashing and preservation. Viewing/downloading is not acceptance of terms and cannot install a language.

Notice archives live separately under `VoiceGuidanceNotices/<category>/<service>/<context-hash>`, with original `notice.xml`, `metadata.enc` and `provenance.json`. They include source URL, package context, size, SHA-1 and SHA-256, without Bluetooth address or serial number. Atomic publication, bounded reads, cancellation and preservation of corrupt existing archives match the package downloader. A failed notice read is shown as an error and remains visibly unavailable; the package can still be preserved, but no installation is enabled.

## Read-only preparation check

After downloading a package, Check Headphones takes another empty-state snapshot in an exclusive MDR transaction. It rereads model, ordinary firmware region, firmware version, supported/current language, language-update status, the exact category/service/serial mapping, update method and battery. The selected Bluetooth address must match the discovery address; the entire request must match the one used to retrieve metadata. Changing firmware, serial, language service or headset requires new discovery. Missing/unknown current language, status, method or charging state fails the check.

Only over-ear CSR methods `10` and `11` pass this preflight. Methods `12`/`13` concern two-earbud CSR and are rejected, along with unknown methods and incomplete parameters. The displayed resume capability comes from the method code and does not establish that OpenXM can recover an interrupted language transfer.

The language status is named `languageUpdateEnabled`, replacing the misleading `languageAvailable`. The reference's [`features/n/a/b.java`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/mdr/j2objc/tandem/features/n/a/b.java) calls this operation `changeUpdateStatus` and sets it before/after transfer. `ENABLE=0` therefore must not be treated as general permission to start a new language installation. A fresh-install preparation check requires it to be disabled; an enabled/unknown state is rejected. The separate on/off availability flag retains its existing meaning.

Battery charge must be **strictly greater than** the reported threshold. The evidence chain is the capability model's `f()` field (labeled Battery Power Threshold), the V1 voice feature's `d()`, the language target's `csr/b/a.java` construction of its update information, [`CsrUpdateController.j()`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-apk--apktool-output/smali/com/sony/songpal/mdr/application/update/csr/CsrUpdateController.smali), and the strict comparison in [`j2objc/a/a.java`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/mdr/j2objc/a/a.java). The smali confirms the threshold is an integer despite the Java decompiler rendering a local as boolean. Voice-language installation additionally requires at least 80% and USB unplugged (separate from the firmware installer’s 50% minimum); those additional restrictions are app policy, not a claim about Sony's threshold. Thresholds of 100 or higher cannot be satisfied and fail explicitly. No transmit-power setter has been established or added.

Preparation reopens and verifies package bytes, original metadata and provenance, and any referenced notice archive. A cached hash or previously displayed notice cannot substitute for the original files. Failed/corrupt archives are preserved. The sheet shows a dated result, current/target language, charge requirement and advertised resume support. Success is not installation authorization, does not accept terms, and is not hardware validation. No update-mode SET or GAIA command is sent. The installer repeats device and archive checks after its explicit final confirmation.

## Native installation and recovery

Check Headphones opens a dedicated V1 control connection after ordinary controls have released it. Only GETs are used for inspection. Install Language requires a successful preparation check; a saved session requires Check Saved Session so the original notice and metadata are visible before installation can be selected. A separate cancel-first native confirmation describes the actual operation and experimental status. Cancelling creates no journal, enables no mode and opens no GAIA connection. Device identity, language, method, power and original files are checked again after the dialog; a changed review is rejected.

The coordinator saves `Library/Application Support/SoundConnect/voice-language-session.json` before enabling language-update mode. Its private 0600 record binds a UUID, Bluetooth address, firmware, exact language category/service, hash of the serial, original/target languages, exact method parameters, archive directories, metadata/package/notice SHA-256 values and transfer phase. It stores no raw serial. Unsupported schemas, invalid state combinations, malformed hashes and unavailable/corrupt original assets fail closed without replacing the record. This journal is separate from `firmware-session.json`.

Normal controls, pairing, settings restoration and automatic control reconnection are reserved while either update journal exists. Both installers use the same kernel lock. The firmware CLI/GUI rejects a pending language session; the language installer rejects a pending firmware session. A lock file's mere existence does not mean an operation is running. The disconnected page and Settings route a language session to Language Update Status, including after app restart or a corrupt saved record.

Immediately before the language-mode SET, native access rereads the same headset's binding, method, current language and power. Sony's target callback uses table-2 `44 01 02 00` and requires exact notification `45 01 02 00`; disabling ends in `01`. OpenXM now implements those transactions only inside an explicitly confirmed installation/cleanup. The [pinned builder](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-apk--apktool-output/smali_classes2/com/sony/songpal/tandemfamily/message/mdr/v1/table2/voiceguidance/x$a.smali) and V1 voice feature writer establish this wire behavior. The status cannot be satisfied by an ordinary parameter response, wrong selector, opposite value, truncated packet or extra bytes.

MDR is closed before GAIA opens. The entire original voice package is streamed by the existing CSR VMU engine, with the last four MD5 bytes as sync ID; it is never parsed or accepted as a pinned firmware image. The journal records uncertainty before GAIA connection, checkpoints before each mutating stage, and records commit before cleanup. An expected reboot reconnects only the original paired headset. Independent post-transfer MDR reads must report the same firmware/service/serial/method, the target language, and disabled language-update mode before the journal is removed. A package-commit notification alone is not success.

Recovery behavior is deliberately explicit:

- Before GAIA could have started, a matching saved preparation may retry either over-ear method `10` or `11`.
- A saved preparation can instead be cancelled only when `transferStarted` is false and its phase is `preparing`. After a separate confirmation, OpenXM rechecks the exact journal and headset, disables language-update mode, and independently verifies the original language and disabled mode before removing the journal. It never opens GAIA or issues an abort. Missing package/notice files do not block this cleanup; existing downloads are preserved. Any uncertain reply, changed identity/language/record or read-back failure retains the session. Transfer battery thresholds do not apply to cleanup.
- After GAIA may have started, only method `11` advertises resumable transfer. The device selects its resume point for the identical sync ID and assets.
- If the target language already runs provisionally, only VMU commit points `3`/`4` are accepted. Point `0` is rejected before start/data/commit commands; the package is never uploaded again in that state.
- A journal marked complete performs mode cleanup and independent language verification only. It does not reopen GAIA, and transfer battery requirements do not block verification after battery depletion.
- A failed transfer closes GAIA before attempting to disable language-update mode. Cleanup also runs when the transfer task was cancelled. Failed cleanup or read-back retains the journal and controls reservation.
- An interrupted method-`10` transfer cannot be automatically restarted. OpenXM preserves the session and explains the limitation. No unverified abort/reset or journal-discard operation is offered.

Sony's actual XM3 preparation text/notice and package still require a live service mapping. The XM4 reference and synthetic test files cannot supply that mapping. These software paths have not been used to install a language on the user's headphones.

## Remaining installation validation

Settings backups now preserve a known current V1 language only when it is also advertised by the freshly read capability. This uses backup format 3; formats 1 and 2 remain readable. No serial, download-service identifiers, update-mode flags or package bytes are copied into the settings file. A different saved language cannot become an ordinary `DeviceChange` or trigger an upload through Restore Selected. Review Language Package dismisses the backup sheet and opens the package sheet with that language selected. It performs no network request or headphone write. Check Sony still requires a fresh international XM3 service mapping, and installation retains its independent preparation and confirmation. Original downloaded package files can now be exported and reopened separately as described below.

Application termination handling now includes active language installation, verification and preparation cancellation. Closing the last window does not automatically terminate during those operations; explicit Quit offers Keep OpenXM Running first and explains the pending language verification. This closes the previous gap where only firmware and settings operations were considered.

1. Capture the actual international XM3 current language, service descriptor and update method on each supported firmware. Do not infer them from another model or region.
2. Retrieve the original XM3 metadata, package and notice through that mapping and establish provenance; then exercise the native download/preparation review on the live headset.
3. Validate a user-confirmed physical language installation, expected reboot, normal-mode cleanup and independent language/firmware read-back. Test interruption recovery only with explicit hardware-test authorization and a concrete recovery plan.
4. Establish a supported recovery/abort path for non-resumable method `10`, if the actual XM3 reports it. The current implementation refuses to guess how to restart an uncertain transfer.

### Additional transfer evidence

The pinned `application/update/csr/d.smali` calls its target-specific `changeUpdateStatus(device, true)` before connecting GAIA, and calls `changeUpdateStatus(device, false)` during finalization after disconnecting GAIA. The language callback is therefore part of session preparation/cleanup, not the ordinary firmware-version check. Its common [`csr/h.java`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/mdr/application/update/csr/h.java) computes the last four bytes of MD5 from the complete package for the VMU sync ID and streams the original package bytes without interpreting firmware records.

The `UpdateMethod` enum identifies `10` as CSR, `11` as resumable CSR, `12` as two-earbud CSR and `13` as resumable two-earbud CSR. Recognizing all four for discovery does not authorize the over-ear updater to use a two-earbud method. The actual XM3 language update-method reply remains missing.

Cancellation research distinguishes preparation cleanup from transfer abort. The pinned Sony [`csr/d` smali](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-apk--apktool-output/smali/com/sony/songpal/mdr/application/update/csr/d.smali) calls `abortAndRestart` only on synchronization errors `0x0081` or `0x0023`, at most once. It sends VMU `07`, waits for `08`, then restarts synchronization. That is not evidence for freely abandoning an uncertain transfer. Its cancellation predicate during `IN_SENDING` requires `UpdateCapability.c()`; the [V1 capability builder](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/mdr/j2objc/devicecapability/tableset1/g.java) sets this field from `UpdateMethod.isResumable()`. [`CsrUpdateState`](https://github.com/egaebel/sony-headphones-hack/blob/ac1d5f8ff8d82a07e7b07d07ecc67c7b37a7b1ed/base-dex2jar.jar.src--files/com/sony/songpal/mdr/application/update/csr/CsrUpdateState.java) also disallows cancellation during installation/completion/finalization. OpenXM therefore adds no generic transfer-abort or journal-discard command. Its preparation-cancellation option uses the existing mode-cleanup transaction and is available only before GAIA could have started.

Byte inspection of the separately downloaded XM4 Dutch sample found **none** of `APPUHDR2`, `PARTDATA`, `APPUPFTR` or `ZARKOV77`. It starts `96 f1 8f 30 53 64 e6 dc`. Its Sony size/SHA-1 match, but its package structure does not validate the XM3 CSR transfer path. The referenced 2,019-byte notice was also retrieved and matched SHA-1 `2455d4c5cf8cf3488fa8b2a2ed36133d2aacf4d0`; it contains locale-specific placeholder disclaimer text. Neither that notice nor the XM4 package substitutes for the actual XM3 assets.

## Portable package files

Settings → Voice Package Files opens the package sheet even when the headphones are disconnected. Export Package saves a version 1 `OpenXM voice package` JSON file containing the unchanged binary, encrypted Sony metadata, optional original notice, and both original provenance records. Each component has a SHA-256 digest. The file records model, language, firmware at discovery, service and package-version labels; it adds no device address, serial request field, local path or update journal. Sony metadata is retained verbatim, including any eligibility rules it contains. This preserves downloaded packages, not a dump of the package currently installed in the headphones.

Open Saved Package reads at most 48,000,000 bytes, checks component limits/hashes and the service-specific metadata envelope, and displays the recorded context. This is an offline inspection, not device eligibility or publisher-signature verification. The file cannot enable installation. It also cannot replace an active language session. A settings-backup handoff rejects a file for a different requested language.

Check Saved Package obtains a fresh international XM3 model/region/service mapping. The recorded model, service and language must match; Sony's original metadata rules are evaluated using the current firmware and serial. Package size/SHA-1, package-version label, required notice and notice structure are checked before any imported archive is published. A changed firmware is allowed only if those original rules still select the saved package. The entire original export, with its original provenance, is retained as `original-backup.json` beside separate archives describing the newly checked device context. Imports are staged and published together; corrupt existing records are retained and rejected. No network fetch or headphone write occurs in this check.

After that check, the existing preparation and final installation confirmation still apply. A saved file does not bypass model/region, update method, battery, original-file revalidation or independent post-install read-back. The generic file format can preserve other model references, but the native XM3 service factory and import matching prevent an XM4 reference from being used on an XM3. Physical installation from an imported XM3 package remains unverified.

The notice's SHA-256 is `6b01feb499136d42d2459f5e9cc7268f75c8a72be51972fe64056cf9a18179b9`. The native URLSession integration test independently downloaded and preserved these same bytes, including leading whitespace, with all 16 locale texts. It is retained as `xm4-dutch-voice-notice.xml` for parser tests and remains clearly labeled as an XM4 placeholder reference.
